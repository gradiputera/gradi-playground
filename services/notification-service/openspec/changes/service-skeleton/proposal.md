# Proposal

## Why

Roadmap step 3, fourth service. payment (Go), ledger (Java) and account (PHP) run on Vercel with the shared skeleton pattern. notification-service now gets the same skeleton in Node.js 24 and TypeScript. As the only event consumer so far, it also gets real webhook signature checks, so roadmap step 4 can connect the dispatcher to a service that already rejects unsigned and replayed deliveries.

The owner chose **Express 5** instead of Hono, which ADR 0002 had recorded. This change records that decision and updates every place that names Hono.

Owning scope: **services/notification-service**, plus the documentation updates for the framework switch (see below).

## What Changes

- **Express app:** `services/notification-service` becomes an Express 5 app in TypeScript, standalone, with npm and its own `package-lock.json`. Node 24 runs the `.ts` sources directly (type stripping), so there is no build step; `tsc --noEmit` typechecks. The service:
  - reads `PORT` (default 80), `DATABASE_URL`, `SUPABASE_URL` and `WEBHOOK_SECRET`, and refuses to start without them;
  - logs one JSON object per line;
  - drains requests for up to 20 seconds on SIGTERM.
- **`GET /health`:** answers `{"status":"ok"}`, with no token needed.
- **Resource-server JWT validation with `jose`:**
  - keys come from the Supabase JWKS with a 5-second timeout, cached for an hour, with at most one refetch every 5 minutes for an unknown key;
  - only ES256 and RS256 are accepted;
  - `iss`, `aud` (`authenticated`), `exp` and `sub` are required;
  - a missing or invalid token gets 401 with `WWW-Authenticate: Bearer`.
- **`POST /events` (webhook signature):** verifies Standard Webhooks signatures, the scheme the platform dispatcher already uses (`eventbus.sign`):
  - HMAC-SHA256 over `id.timestamp.raw-body`, with the `whsec_` key;
  - a timing-safe comparison;
  - a 5-minute timestamp tolerance against replay.

  Failures get 401. Verified events get 501 until roadmap step 4 processes them; nothing is written, so the dispatcher redelivers later.
- **`POST /sandbox/reset`:** requires a valid token and answers 501 until roadmap step 5. It writes nothing.
- **Contract:** `contracts/openapi/notification.yaml` gains the two 501 responses. The change is additive and checked with oasdiff.
- **Migrations:** generated by Drizzle Kit from `src/db/schema.ts`, and applied at startup by a small migrator of the service's own. It reads Drizzle's migration files and writes Drizzle's history format into `notification.__drizzle_migrations`. Drizzle's built-in migrator always runs `CREATE SCHEMA IF NOT EXISTS`, which the service role is not allowed to run. Migration 0000 creates `inbox`: the event ids already processed, for idempotent consumption in step 4.
- **Container:** `node:24.22.3-trixie-slim` installs the production dependencies; `gcr.io/distroless/nodejs24-debian13:nonroot` runs them as a non-root user on port 8080. `vercel.json` selects the Container preset.
- **Tests:** Node's built-in test runner:
  - unit and HTTP tests with no network: the JWT rules, the webhook signature rules, the routes, 401, 501, 404 and 405;
  - integration tests against local Supabase: migrations and the history table in `notification`, a no-op rerun, the role refused other schemas, and a real Supabase guest token accepted.
- **CI:** a new `notification-service` workflow runs:
  - `npm ci`, the typecheck and `openspec validate`;
  - oasdiff (PRs);
  - all 17 tests against the local stack, with a check that none were skipped;
  - a Docker build and a container smoke test, including an unsigned webhook answering 401.
- **Dependabot:** watches npm and the Dockerfile base images for the service.
- **Docs:** `README.md` and `.env.example`, including the owner's hosted setup and the webhook secret.

Files outside the service folder:
- the service's own CI wiring, which GitHub only reads from the root: `.github/workflows/notification-service.yml` and two `.github/dependabot.yml` entries;
- the framework switch:
  - an amendment note and the table row in `architecture/adr/0002-polyglot-services.md`;
  - one line each in `CLAUDE.md`, `architecture/c4/README.md` and `openspec/config.yaml`;
  - three lines in `README.md`;
  - the skills list on the main page (`apps/web/app/content/profile.ts`: "Node.js / Express");
  - the context line in `services/notification-service/openspec/config.yaml`.

  The owner chose to fold these into this change rather than a separate one.

Out of scope:
- consuming events (inbox writes), the mail module, email caps and masking, sandbox reset logic, guest restrictions, the site fault flag and telemetry (roadmap steps 4 to 6);
- setting the dispatcher's endpoint URL for the notification consumer (step 4);
- reporting-service;
- any hosted action (owner actions).

## Capabilities

### New Capabilities
None.

### Modified Capabilities
- `service-baseline`:
  - token validation gains concrete rules;
  - adds requirements for the listening port and required configuration (including `WEBHOOK_SECRET`), startup migrations, graceful shutdown, and the authenticated 501 on sandbox reset.
- `event-notifications`: makes the signature scheme concrete (Standard Webhooks, `v1,` HMAC-SHA256), fixes the replay tolerance at 5 minutes, and adds the 501 behaviour for verified events before processing exists. There is no email template or cap change (ADR 0014 is unchanged).
