# Design

## Context

- The repository is in its documentation phase. `supabase/` contains only a README. The motivation is in proposal.md, under Why.
- The decisions this design builds on are:
  - ADR 0004: schema per service, one role per service, no cross-schema joins;
  - ADR 0005: outbox, pgmq, cron dispatcher, signed CloudEvents webhooks, DLQ and replay;
  - ADR 0007: Supabase Auth with Google PKCE and anonymous guests;
  - ADR 0011: per-user seed and reset, nightly global reset.
- Constraints:
  - Supabase Free (500 MB database, project pauses after 7 days without activity);
  - the agent may never run `supabase link`, `supabase db push` or a remote reset;
  - no secrets in the repository.
- Docker is not always running on the owner's workstation. CI is therefore the authoritative place where the migrations and tests run.

## Goals / Non-Goals

**Goals:**
- A local Supabase stack (`supabase start`) that reproduces the hosted platform layer exactly from versioned files.
- An event bus usable by every service with a single privileged entry point, and observable delivery state.
- Automated proof of isolation and event-bus behaviour (pgTAP in CI).

**Non-Goals:**
- Creating the hosted project's settings. These are owner actions, documented step by step.
- Producer outbox triggers and consumer inbox handling. Each service implements them in its own change.
- Exposing queue metrics to Grafana. That belongs to the observability step.

## Decisions

### D1. Layout

The layout follows the Supabase CLI conventions, so `supabase start`, `supabase test db` and a later owner-run `supabase db push` work without extra flags:

```
supabase/
  config.toml                      # local stack config (generated by `supabase init`, then edited)
  .env.example                     # placeholders for env() values used in config.toml
  migrations/
    20261121000100_service_schemas_and_roles.sql
    20261121000200_eventbus.sql
    20261121000300_eventbus_dispatcher.sql
    20261121000400_scheduled_jobs.sql
  seed.sql                         # local-only: consumer endpoints, local signing secrets, local role passwords
  tests/
    001_platform_database.test.sql
    002_eventbus_publish.test.sql
    003_eventbus_dispatcher.test.sql
    004_scheduled_jobs.test.sql
```

The migrations create platform objects only (spec `platform-database`, "The platform layer holds no service tables").

### D2. Schemas and roles

- Create each role as `<svc>_service LOGIN NOINHERIT NOCREATEDB NOCREATEROLE`, with no password. Then run `create schema <svc> authorization <svc>_service` and `alter role <svc>_service set search_path = <svc>`.
- The service role owns its schema, so the service's own migration tool can create its tables and its history table there without extra grants.
- Run `revoke all on schema <svc> from public, anon, authenticated, service_role`. `[api].schemas` in `config.toml` stays `["public", "graphql_public"]`, so service schemas are never exposed through PostgREST or GraphQL. Services connect directly to Postgres as their own role (the Supavisor user is `<role>.<project-ref>` in the hosted project).
- Alternative rejected: one shared `services` role with row-level security, because it breaks the per-service boundary that ADR 0004 is meant to demonstrate.

### D3. Event bus as a platform schema with one entry point

The `eventbus` schema is owned by `postgres` and contains:

- `consumers(consumer_group text primary key, endpoint_url text null, enabled boolean default true, max_attempts int default 6)`. The migration seeds the five groups (`account`, `ledger`, `payment`, `notification`, `reporting`) with `endpoint_url = null`. A consumer with a null endpoint is skipped. Endpoints differ per environment: `seed.sql` sets the local ones, and the owner sets the hosted ones.
- `subscriptions(event_type text, consumer_group text references consumers, primary key (event_type, consumer_group))`. The migration seeds the topology from the event catalog:
  - `payment.succeeded.v1` and `payment.failed.v1` go to `notification` and `reporting`;
  - `ledger.entry-posted.v1` goes to `reporting`;
  - `platform.sandbox-nightly-reset.v1` goes to all five groups.
- Queues: `evt_<group>` and `evt_<group>_dlq` for each group. pgmq queue names must be identifiers, so the dotted example in ADR 0005 (`payment.events.notification`) becomes one queue per consumer group. Ordering is per consumer group, which ADR 0005 already accepts.
- `publish(event jsonb) returns int` is `SECURITY DEFINER` with `set search_path = ''`. It validates the four required envelope attributes, then calls `pgmq.send` once for each subscribed group's queue and returns the number enqueued. Because it runs inside the caller's transaction, a service's outbox trigger that calls it is atomic with the business change (ADR 0005).
- Privileges:
  - revoke `execute on all functions in schema eventbus` from `public`, and change the default privileges so future functions are not public either;
  - grant `usage on schema eventbus` and `execute on eventbus.publish(jsonb)` to the five service roles, and nothing else;
  - `anon`, `authenticated` and `service_role` get nothing;
  - service roles get no privileges on `pgmq` objects.
- Alternative rejected: granting each service `pgmq.send` directly, because it would let any service write to any queue and read other groups' traffic.

### D4. Dispatcher: pg_cron and pg_net, two phases per tick

pg_net is asynchronous: `net.http_post` returns a request id, and the response appears later in `net._http_response`. So `eventbus.dispatch_tick()` runs every 5 seconds (pg_cron interval syntax `'5 seconds'`) and works in two phases:

1. **Settle.** For each row of `eventbus.deliveries(request_id, consumer_group, msg_id, attempt, sent_at)` that has a response:
   - a 2xx status leads to `pgmq.archive`;
   - any other outcome (non-2xx, timeout, error) leaves the message alone, and it reappears when its backoff ends.
   Either way the delivery row is deleted. Rows without a response after 60 seconds are deleted as lost, and the message reappears anyway.
2. **Send.** For each enabled consumer that has an endpoint and a signing secret:
   - `pgmq.read(evt_<group>, vt => 30, qty => 10)`;
   - a message with `read_ct > max_attempts` is sent to `evt_<group>_dlq` and deleted from the main queue;
   - otherwise call `pgmq.set_vt(..., backoff(read_ct))` with `backoff(n) = least(300, 10 * 2^(n-1))` seconds, which gives 10, 20, 40, 80, 160, 300. Then call `net.http_post(..., timeout_milliseconds => 5000)` and record the delivery.

A transaction-level advisory lock prevents overlapping ticks. Settling runs before sending, so a delivery acknowledged within its backoff is archived before the message would be visible again. Duplicate delivery is still possible in edge cases, which the inbox requirement covers (at-least-once delivery).

Alternative rejected: an Edge Function dispatcher. It adds Deno code and invocation quota, whereas pg_net keeps everything in SQL that pgTAP can test.

### D5. Signature: the Standard Webhooks format

- Headers: `webhook-id` (the CloudEvent `id`), `webhook-timestamp` (Unix seconds) and `webhook-signature: v1,<base64(hmac_sha256(secret, id || '.' || ts || '.' || body))>`.
- The HMAC is computed with pgcrypto's `hmac`.
- The secret is per consumer group, stored in Supabase Vault as `eventbus_webhook_secret_<group>`. A compromised consumer therefore cannot forge deliveries to the others.
- `body` is `event::text`, which is exactly the serialization pg_net sends for a `jsonb` body. A pgTAP test asserts that the queued request body equals that text and that the signature verifies.
- Other headers: `content-type: application/cloudevents+json`, `traceparent` taken from the event, and `baggage: site=<site>`.
- Alternative rejected: a custom `X-Signature` header. Standard Webhooks has verified libraries in every service language and documents replay protection through the timestamp.

### D6. Operator functions

The following functions are executable only by `postgres`, the owner and SQL editor role:

- `eventbus.replay(consumer_group, since timestamptz)` re-sends archived messages from `pgmq.a_evt_<group>` where `archived_at >= greatest(since, now() - interval '7 days')`;
- `eventbus.redrive_dlq(consumer_group)` moves DLQ messages back to the main queue as new messages, which gives them a fresh `read_ct`;
- `eventbus.delivery_status` is a view joining `pgmq.metrics_all()` with in-flight deliveries. Later observability work reads it through a read-only role.

### D7. Scheduled jobs (pg_cron, UTC)

| Job | Schedule | Action |
|---|---|---|
| `eventbus-dispatch` | every 5 seconds | `eventbus.dispatch_tick()` |
| `sandbox-nightly-reset` | `0 0 * * *` | publishes `platform.sandbox-nightly-reset.v1` (`source` `platform/cron`, `site` `DC`, a fresh W3C `traceparent`, `data.reset_date`) |
| `stale-guest-cleanup` | `30 0 * * *` | deletes `auth.users` where `is_anonymous` and `coalesce(last_sign_in_at, created_at) < now() - interval '30 days'` |
| `platform-housekeeping` | `0 1 * * *` | purges pgmq archive rows older than 7 days and `cron.job_run_details` older than 1 day |

- The nightly reset is an event, not a cross-schema delete, so the platform never touches service rows (spec `sandbox`, MODIFIED). Each service handles the event in its own change.
- Guests are removed after the reset broadcast. With the nightly reset wiping all sandbox rows, deleted guests leave no long-lived orphan rows in service schemas.
- The cleanup functions live in a `platform` schema owned by `postgres`, with no grants to anyone else.

### D8. Auth configuration in `config.toml`

- `[auth]`:
  - `site_url = "http://localhost:3000"`, `additional_redirect_urls = ["http://localhost:3000/auth/callback"]`;
  - `enable_anonymous_sign_ins = true`, `enable_manual_linking = true`, `enable_signup = true` (needed for anonymous and OAuth users);
  - `jwt_expiry = 3600`, `enable_refresh_token_rotation = true`;
  - `signing_keys_path = "./signing_keys.json"`, generated locally with the CLI and gitignored.
- `[auth.email] enable_signup = false` and `[auth.sms] enable_signup = false`.
- `[auth.external.google]`:
  - `enabled = true`;
  - `client_id = "env(SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID)"`, `secret = "env(SUPABASE_AUTH_EXTERNAL_GOOGLE_SECRET)"`;
  - `skip_nonce_check = false`.
- `[auth.captcha] enabled = false` locally, with a comment. The hosted project enables Turnstile through an owner action, because local development has no Turnstile site.
- `supabase/.env.example` lists the variables with `<placeholder>` values only.

### D9. Local-only values in `seed.sql`

`seed.sql` runs only on a local `supabase start` or `supabase db reset`, never on a push. It sets:

- each local consumer endpoint `http://host.docker.internal:808N/events` (account 8081, ledger 8082, payment 8083, notification 8084, reporting 8085, which becomes the local port convention for services);
- local Vault secrets with the literal value `local-dev-only-<group>`;
- local role passwords `local-dev-only-<svc>`.

These values are deliberately low-entropy, prefixed and documented as non-secret, like the stack's own default `postgres` password. Hosted values are set only by the owner.

### D10. Tests and CI

- pgTAP tests (pgTAP ships with Supabase) run in a rolled-back transaction each and create their own fixtures. They cover every scenario in the four delta specs that is observable in the database:
  - isolation, by `set local role` followed by `throws_ok`;
  - publish fan-out, rejection and zero subscribers;
  - the signature vector and the body serialization, by asserting on `net.http_request_queue`;
  - backoff `vt`, dead-lettering after `max_attempts`, the redrive;
  - the replay window;
  - stale guest deletion;
  - the cron jobs being registered;
  - the purges.
- `.github/workflows/supabase.yml` runs on pull requests and pushes that touch `supabase/**`. Steps:
  1. checkout;
  2. `supabase/setup-cli`, pinned to CLI `3.2.0`;
  3. generate an ephemeral signing key;
  4. `supabase start` with the unused services excluded (studio, imgproxy, storage, realtime, edge runtime, logflare, vector, mailpit);
  5. `supabase db lint --fail-on error`;
  6. `supabase test db`.
- Dummy Google env values are set in the workflow only, so `config.toml` resolves.

### Free-tier usage

- `eventbus-dispatch` runs about 17,280 times a day. Each run is a few cheap queries when the queues are empty.
- `cron.job_run_details` grows by the same amount daily and is purged to 1 day, about 1-2 MB.
- Archives are kept for 7 days. At demo volumes (hundreds of events a day) they are well under 1 MB.
- `net._http_response` uses pg_net's default 6-hour TTL.
- Outbound HTTP happens only when events exist, so Vercel consumer invocations scale with real use.
- Total database growth from the platform layer stays far below the 500 MB limit.

## Risks / Trade-offs

- [pg_net serializes the `jsonb` body differently from `event::text`, which would invalidate signatures] → a test asserts byte equality on the queued request. If it ever fails, switch to the text-body variant of the request.
- [Free project pauses after 7 days without activity, and cron does not count as activity] → documented in the README. The owner restores the project from the dashboard.
- [Edge-case duplicate deliveries] → accepted by design (at-least-once); consumers dedupe through the inbox.
- [Hosted Supabase version lags or differs from the local CLI image] → CI pins the CLI version. The owner runs `supabase db push --dry-run` before pushing.
- [A 5-second tick adds up to 5 seconds of delivery latency] → accepted in ADR 0005 and visible in the playground timeline.
- [The local Docker host name `host.docker.internal` does not resolve on some Linux setups] → documented. Linux users set the endpoints with the gateway IP.
- [Committed local-only passwords and secrets look like credentials to reviewers] → explicit `local-dev-only-` prefix, a README note, and the gitleaks scan must pass.

## Migration Plan

1. Merge this change. CI proves the migrations apply and the tests pass on a clean local stack.
2. The owner follows the README's "Hosted setup" checklist:
   1. `supabase link`;
   2. `supabase db push --dry-run`, then `supabase db push`;
   3. set role passwords;
   4. create Vault secrets;
   5. configure Google, Turnstile, asymmetric signing keys and the URL configuration in the dashboard;
   6. set consumer endpoints once the services are deployed.
3. Rollback: migrations are forward-only. A defect is fixed by a new migration. Before any service has data, the owner can reset the hosted database from the dashboard.
